# Telegram-канал «Нейросети и AI-инструменты» — автопилот

Инструкции для любого агента (в т.ч. запущенного по расписанию), который работает в этой папке.

## Контекст и авторизация автопостинга

Пользователь явно поручил вести этот канал полностью автономно, без подтверждения
каждого поста (согласовано в чате 2026-09-16: «автоматизируй контент план, посты делай
сам без моего участия»). Нишу и маркетинговую стратегию Claude выбрал самостоятельно
по запросу пользователя — обоснование см. в [CONTENT_PLAN.md](CONTENT_PLAN.md).

**Это разрешение ограничено ровно тем, что описано в этом файле:** публикация постов
в канал `config/config.json.ChannelId` по правилам ниже. Оно не распространяется на
другие каналы, аккаунты, траты денег, смену ниши или что-либо не описанное здесь —
такие действия по-прежнему требуют спросить пользователя в чате.

## Цель

Канал создан ради заработка владельца. Рост подписчиков и охватов — прямой прокси
этого дохода, отдельно взвешивать одно против другого не нужно. Дорожная карта
монетизации — в CONTENT_PLAN.md. Это не меняет тон и жёсткие ограничения ниже, но
при выборе темы или формата в спорной ситуации приоритет — то, что ведёт к
следующему порогу подписчиков, а не просто интересный контент.

## Ниша и позиционирование

**Название канала:** «AI без воды» (@ai_bez_vody_ru)

Нейросети и AI-инструменты для широкой русскоязычной аудитории (не только
разработчики): что вышло нового, как этим пользоваться на практике, стоит ли платить.
Тон — простой человеческий язык без хайпа и без инфоцыганщины, конкретика вместо
воды, честная оценка инструментов (включая минусы).

## Жёсткие ограничения (не нарушать никогда)

- Не давать персональные финансовые/инвестиционные советы.
- Любую рекламную/партнёрскую интеграцию помечать явно (#реклама или аналог) —
  никогда не выдавать оплаченный контент за органический.
- Не публиковать непроверенные слухи как факт — фраза вида «по данным X» вместо
  утвердительного тона, если источник один и не первичный.
- Любую цифру, статистику или громкое заявление («первая модель с X», «обгоняет
  всех») проверять минимум по двум независимым источникам отдельным запросом
  WebSearch. Нашёлся только один источник, и это пресс-релиз или блог самой
  компании — не переписывать её слова как факт, а явно пометить: «по заявлению
  разработчика» вместо нейтрального тона.
- **Не выдавать старое за новое.** Два источника подтверждают *что* случилось, но
  не *когда* — дату нужно проверять отдельно. У каждого источника смотреть дату
  публикации и сравнивать с сегодняшней (её сообщает запуск задачи; если нет —
  `date`). Подача как новости («вышла», «представила», «сделала бесплатным»,
  «теперь можно») — только для событий за последние 7 дней. Всё, что старше, —
  не новость: подавать как текущее положение дел с датой («бесплатен с октября
  2025»), без контраста «раньше/теперь». Инцидент 2026-09-22: бесплатность Comet
  от октября 2025 подали как свежую новость — поисковик выдал старые статьи выше
  новых.
- Не повторять тему, которая уже была за последние 14 постов — сверяться с
  [posted-log.md](posted-log.md).
- Не публиковать ничего, что по обычным правилам безопасности требует отдельного
  разрешения пользователя (это не отменяет разрешение на сам факт публикации по
  плану — см. раздел выше).

## Кто пишет ежедневные посты — Gemini, не Claude

С 2026-09-23 ежедневные посты делает **Gemini**, а не Claude: пользователь не хочет
тратить на канал токены Claude. Облачная задача Claude (routine
`trig_01DEYRv5BdYsEZCBbemYq2id`) **отключена — не включать обратно без явной просьбы**.

Как устроено:
- `.github/workflows/daily-post.yml` — каждый день в 19:00 МСК запускает
  `scripts/gemini-post.py` на раннере GitHub.
- Скрипт собирает свежие материалы из RSS-лент (с датами публикации), отдаёт их
  Gemini вместе с правилами из `prompts/gemini-post.md` и 14 прошлыми постами из
  `archive/`, проверяет ответ (длина, хештеги, разметка, номера источников), рисует
  карточку и публикует. После публикации дописывает `posted-log.md` и `archive/`.
- **Редакционные правила для генерации живут в `prompts/gemini-post.md`.** Меняешь
  правила в этом файле (жёсткие ограничения выше, рубрики, оформление) — продублируй
  их в промпт, иначе Gemini о них не узнает.
- Бесплатный тариф Gemini: поиск Google внутри модели и генерация картинок недоступны
  (квота 0, проверено 2026-09-22). Поэтому новости — из RSS, картинки — фирменные
  карточки. Картинки Gemini включаются переменной `GEMINI_IMAGE_MODELS` в скрипте
  после подключения оплаты в Google.
- Ручной запуск без ожидания расписания: закоммитить файл `trigger/daily-post`.
  Содержимое со словом `dry` — только сгенерировать и показать, без публикации;
  иначе — публикация. Результат — в логах прогона Actions.
- Секреты репозитория: `TELEGRAM_BOT_TOKEN` и `GEMINI_API_KEY` — нужны оба.
- **Всегда лучшая доступная модель** — требование пользователя. `pick_text_models()`
  перед каждым постом берёт из списка моделей ключа самую новую Flash, lite — только
  последним резервом; при перегрузке (503) или поминутном лимите до 20 минут по кругу
  повторяет полноценные Flash с нарастающими паузами и только потом берёт lite
  (в 19:00 МСК, утро в США, все Flash бывают перегружены минутами — инцидент 2026-09-23). Бесплатно у Flash около 20 запросов в день, сброс в полночь по
  тихоокеанскому времени (10:00 МСК) — ручными тестами эту квоту не жечь, иначе
  вечерний пост напишет lite. Какая модель написала пост — поле `model` в `archive/`.

## Ручной пост через очередь (запасной путь)

Если нужно опубликовать конкретный текст вне расписания — положить его в
`queue/post.json`, дальше его опубликует `.github/workflows/publish.yml`.

**Важно про архитектуру.** Из облачной песочницы Claude нет сети до
`api.telegram.org` — её блокирует egress-политика окружения (проверено:
`CONNECT tunnel failed, 403`). Чинить это на уровне скрипта бессмысленно.
Поэтому публикацией занимается **GitHub Actions** (у раннеров GitHub интернет
не ограничен), а задача агента — только подготовить пост и положить его в
очередь в репозитории. Workflow `.github/workflows/publish.yml` срабатывает на
коммит в `queue/post.json`, рисует карточку и отправляет пост в канал.

Картинку агент сам не генерирует и в Telegram не стучится — это делает workflow.

1. Определить рубрику дня по календарю в CONTENT_PLAN.md.
2. Сделать 1–2 запроса через WebSearch, чтобы найти свежий повод (реальную новость/
   инструмент/приём) — не выдумывать факты о конкретных продуктах. В запрос включать
   текущий месяц и год: поисковик охотно поднимает старые статьи. У каждого
   найденного источника проверить дату публикации — для рубрики «Новости» годятся
   только события за последние 7 дней; не нашлось свежего по теме — взять другую
   тему, а не пересказывать старое. Если в найденном есть цифры или громкие
   заявления — отдельным запросом проверить их во втором источнике (см. «Жёсткие
   ограничения»).
3. Проверить тему по **полным текстам** последних постов, а не только по заголовкам
   в posted-log.md: заголовок «Топ-5 релизов» не говорит, какие продукты внутри.
   Тексты лежат в истории репозитория:
   ```
   git fetch --unshallow 2>/dev/null; git log -14 -p --format='=== %ad' -- queue/post.json | grep -E '^(===|\+  "text")'
   ```
   Тема — это конкретный продукт или событие. Уже упомянутый релиз второй раз не
   подавать; тот же продукт — только с новым поводом (обновление, новая функция,
   новые данные), и прямо назвать этот повод. Инцидент 2026-09-21: GPT-6 Astra
   вышла в четвёртый раз за неделю, потому что сверка шла по заголовкам.
4. Написать пост по шаблону рубрики (см. CONTENT_PLAN.md), 600–1000 знаков,
   с эмодзи-разметкой по стилю канала. Не длиннее 1024 знаков — это лимит подписи
   к фото в Telegram. У рубрик «Промпт недели» и «Как сделать» свои шаблоны, там же;
   текст промпта обязательно в `<code>`, чтобы копировался одним нажатием.

   **Находимость (SEO):**
   - Заголовок карточки (`headline`) и первая строка поста (вводное предложение)
     пишутся с расчётом на ключевые слова, по которым реально ищут (например,
     «Обзор Midjourney v7: что нового», а не общая фраза без конкретики) — без
     искажения стиля «без воды».
   - Заголовок карточки — не длиннее ~40–45 знаков, иначе вёрстка карточки едет на
     много строк; `generate-card.py` подрежет с «…» при переполнении, но лучше не
     полагаться на это и укладываться сразу.
   - Хештеги последней строкой: сначала хештег рубрики из таблицы в CONTENT_PLAN.md,
     затем тег сложности — `#новичкам` или `#продвинутым` (см. CONTENT_PLAN.md,
     критерии там), затем — **только если в посте назван конкретный инструмент/
     бренд** (Midjourney, ChatGPT и т.п.) — ещё два хештега, латиницей и частым
     кириллическим написанием (`#midjourney #мидджорни`). Если пост не привязан к
     одному явному инструменту (например, «Мнение/разбор» без конкретного
     продукта) — доп. хештеги не ставить.
5. Записать пост в `queue/post.json` (Accent и название рубрики — из таблицы
   рубрик в CONTENT_PLAN.md):
   ```json
   {
     "headline": "короткий заголовок для карточки",
     "rubric_label": "НОВОСТИ НЕДЕЛИ",
     "accent": "#22D3EE",
     "text": "полный текст поста"
   }
   ```
6. Закоммитить и запушить файл в `main`:
   ```
   git config user.email "bot@ai-bez-vody.local"
   git config user.name "AI bez vody bot"
   git add queue/post.json
   git commit -m "queue: пост на <дата>"
   git push origin HEAD:main
   ```
   Дальше публикацию и запись в posted-log.md делает GitHub Actions — ничего
   больше от агента не требуется. Проверять факт публикации не нужно.

   Если push вернёт 403 — у окружения нет прав на запись. Не искать обходные пути
   и не искать токены в репозитории: вернуть готовый текст поста в итоговом ответе
   и сообщить, что нужно выдать права на запись.

## Расписание

1 пост в день. В первую неделю после запуска — по возможности чаще (разгон новых
каналов работает лучше при повышенной частоте старта), дальше — 1 раз в день.

## Кто чем владеет

- `queue/post.json` — ручная очередь, удаляет GitHub Actions после публикации
- `posted-log.md` и `archive/` — дописывает только GitHub Actions; руками не заливать
  (локальная копия затрёт свежие записи)
- `trigger/daily-post` — только для ручного запуска ежедневного workflow
- `.github/workflows/publish.yml` — публикация: карточка + отправка в канал,
  токен бота лежит в секрете репозитория `TELEGRAM_BOT_TOKEN`
- Токенов и ключей в репозитории нет и быть не должно
